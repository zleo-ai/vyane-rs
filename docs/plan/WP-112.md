# WP-112 — keep MCP workflow daemon mocks responsive

## Outcome

Run `mcp_workflow_tools_use_the_authenticated_resident_daemon` on a two-worker
Tokio runtime so the MCP client, resident daemon, and Wiremock target can make
independent progress after earlier acceptance fixtures in the same process.

Production MCP, daemon, and workflow behavior do not change.

## Failure evidence

Main run `30520725887` at merge commit
`d41ba8e7b5437cb466517eb98de0d18eb0c67aa6` passed release-gate, MSRV, and
coverage. macOS failed
`mcp_workflow_tools_use_the_authenticated_resident_daemon` at the
`submitted["caller_id"]` assertion with `left: Null` for the expected UUIDv7
caller id. Ubuntu was cancelled by matrix fail-fast.

The fixture starts Wiremock, a detached daemon, and an MCP stdio child on the
default current-thread test runtime, then submits a workflow that needs the
mock target. A null `caller_id` indicates the MCP tool returned a non-success
payload rather than the durable admission response, consistent with mock /
control-plane starvation under full-suite scheduling. A two-worker runtime
preserves the intended concurrency without widening production budgets.

## Acceptance

1. The fixture uses an explicit two-worker Tokio runtime.
2. Existing assertions and budgets remain unchanged.
3. No production code or CI process-boundary changes.
4. Local exact and full-binary runs, gates, review, PR CI, and exact
   merged-main CI pass.
