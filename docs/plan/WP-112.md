# WP-112 — keep resident workflow daemon fixtures independently schedulable

## Outcome

1. Run `mcp_workflow_tools_use_the_authenticated_resident_daemon` on a
   two-worker Tokio runtime.
2. Make `poll_workflow_terminal` async: status CLI calls run on
   `spawn_blocking`, and inter-poll waits use `tokio::time::sleep` so Wiremock
   keeps a live runtime worker.
3. Run
   `submitted_workflow_outlives_cli_and_explicit_id_retry_is_idempotent` in a
   fresh CI process after the rest of the CLI suite, for both normal and
   coverage jobs.

Production MCP, daemon, and workflow behavior do not change. Existing fixture
budgets and assertions stay the same.

## Failure evidence

Main run `30520725887` at `d41ba8e` failed macOS on the MCP fixture with a null
submit `caller_id`. PR #64 then failed Ubuntu on
`submitted_workflow_outlives_cli_and_explicit_id_retry_is_idempotent` with
`last state = running` for the full 120s budget even though that fixture
already used two Tokio workers. Blocking status polling plus earlier daemon
fixtures left Wiremock unable to finish the delayed target.

## Acceptance

1. MCP fixture uses two Tokio workers.
2. Workflow terminal polling is async and offloads blocking CLI status.
3. CI isolates the long dual-path workflow fixture in a fresh process.
4. Budgets/assertions and production code are unchanged.
5. Local binaries, gates, review, PR CI, and exact merged-main CI pass.
