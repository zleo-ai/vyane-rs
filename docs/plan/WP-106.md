# WP-106 — keep the resident workflow mock responsive

## Outcome

Keep the Ubuntu main test gate bounded by giving the resident workflow
acceptance fixture an explicit two-thread Tokio runtime. Blocking CLI
subprocess calls and status polling then cannot starve the Wiremock target that
must concurrently serve the detached daemon.

Production workflow, daemon, timeout, and retry behavior do not change.

## Failure evidence

Main run `30511984733` at merge commit
`780d4d3c2b0795b7cb131da439b3e589d63f7ecd` passed release-gate, MSRV,
coverage, and macOS. Ubuntu completed the other two
`daemon_workflow_acceptance` fixtures before
`submitted_workflow_outlives_cli_and_explicit_id_retry_is_idempotent` remained
in `running` state until its existing 120-second terminal budget expired.

The same exact source passed the complete Ubuntu test job on PR #60, but an
exact-name repetition also reproduced the 120-second stall locally. Process
isolation alone is therefore insufficient.

The fixture starts Wiremock on its Tokio runtime, then uses blocking CLI
subprocess calls and `std::thread::sleep` while the detached daemon waits on
that mock target. Tokio's default current-thread test runtime can starve the
mock server during those blocking sections. A two-worker runtime preserves the
intended concurrency without changing any functional budget.

## Acceptance

1. The exact workflow fixture keeps Wiremock responsive while it performs
   blocking CLI polling.
2. Normal and coverage jobs retain their complete existing test sets and
   process boundaries.
3. No test is ignored and no assertion, production timeout, or test budget is
   widened.
4. Local exact split commands, formatting, Clippy, MSRV, release gate, parity,
   independent review, PR CI, and exact merged-main CI pass on immutable heads.
