# WP-91 — configurable native tool decisions

## Goal

Expose the native/Canto tool-level `allow` / `ask` / `deny` classifier as a
bounded per-submission policy with independent user, project, explicit, and
managed config ceilings.

This package does not add tools or capabilities. Filesystem writes, command
execution, command networking, web search, and web fetch remain explicit
request opt-ins with their existing capability policies and OS enforcement.

## Decision model

- The exact registered tool set supplies the base allowlist and remains
  deny-by-default.
- A request may add one ordered decision layer.
- Every configured `[native_permissions.tool_policy]` contributes another
  independent layer. Config files never grant a tool by themselves.
- Within one layer, the last matching rule wins.
- Across the base policy, request layer, and every config layer, the strictest
  result wins: `deny > ask > allow`.
- Non-overridable security floors remain final.
- Tool names, argument names, regex sources, rule counts, matcher counts, and
  total policy bytes are bounded and validated before a paid model request.
- The ordered request and config layers are frozen into the durable native
  spool policy digest, so an idempotent retry with changed rules conflicts.

Example:

```toml
[native_permissions.tool_policy]
default = "allow"

[[native_permissions.tool_policy.rules]]
tool = "run_command"
effect = "ask"

[native_permissions.tool_policy.rules.arguments]
program = "^cargo$"
```

An `allow` result means only that this layer adds no further restriction. It
cannot register `run_command`, widen its executable allowlist, expose network,
or override an `ask`, `deny`, or protected floor from another layer.

## Delivery

1. Add a closed, serializable, bounded rule vocabulary and compile it into the
   existing permission matcher.
2. Preserve all request and config layers through native admission and the
   durable policy digest.
3. Apply the frozen layers to the real native turn driver.
4. Cover layer ordering, strictest-wins composition, absent-tool behavior,
   bounded rejection, `ask` stop behavior, and retry drift.
5. Update the example config, roadmap, and parity ledger without claiming
   approval resume.

## Deliberate boundary

`ask` still produces a canonical call-bound approval plan and stops the run
without executing the tool or replaying the model. An owner-scoped approval
store, expiry, one-shot consumption, policy/workdir drift handling, and exact
resume semantics form a later package. Those product and lifecycle semantics
need Grill/Eosphor alignment before implementation; WP-91 does not invent
them.
