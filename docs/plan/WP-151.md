# WP-151 — bounded durable workflow output projection

Status: implementation complete on `feat/wp151-workflow-output-projection`; independent review CLEAN (P3 only) on prior head, rebased as WP-151.
Driver for the public half of the Vyane Paw VP-15 phase-one requirement: a
succeeded durable workflow must expose a redacted, size-bounded answer on the
existing lifecycle view before any consumer can project it.

Note: this package was initially drafted under the WP-127 id; that number was
taken by the shared-resident native submit CI isolation package on `main`, so
the plan lives as WP-151.

Cross-repo: private integration package **Vyane Paw VP-15** phase one. Phase
two (product result contract and end-to-end evidence) stays in that repository
and must not start until this package is merged and the consumer stable lock is
promoted.

## Goal

Extend the authenticated MCP/daemon workflow lifecycle projection so a
**succeeded** durable workflow returns a single bounded `output` field (or an
explicit omission flag) without weakening the WP-62 redaction boundary.

Submit → status → cancel remains the product surface. No new MCP tool name is
required.

## Motivation

WP-62 deliberately projects only `caller_id`, `state`, and optional
`failure_code`. The resident daemon status path already loads the durable
journal but returns only a body-free `WorkflowJournalSummary` (counts, no step
text). A consumer therefore cannot retrieve the answer of a finished workflow
through `vyane_workflow_status`.

Vyane Paw's durable product path is currently status-only for the same reason.
Request-bound `vyane_dispatch` already returns bounded `output` /
`output_omitted`; durable control should grow an analogous, allowlisted
projection rather than a second ad-hoc tool.

## Current facts (origin/main at branch point)

| Layer | Behavior today |
| --- | --- |
| `vyane_mcp::WorkflowView` | `caller_id`, `state`, `failure_code` only; comment: excludes ownership, controller, lease, authentication, paths, prompts, and raw errors |
| `AuthenticatedWorkflowControl` | maps `TaskRecord` only; drops `WorkflowTaskView.journal` |
| Daemon `WorkflowTaskView` | `task` + optional body-free journal summary |
| Full journal on disk | step `output` / fan-out `outputs` live under `$VYANE_DATA_DIR/workflows/<id>.json`; task SQLite never stores bodies |
| Tool wire budget | MCP success payloads still capped by `MAX_TOOL_OUTPUT_BYTES` (1 MiB) |

## Contract

### Additive public view

`WorkflowView` gains two optional/conditional fields:

| Field | When present | Meaning |
| --- | --- | --- |
| `output` | `state == succeeded` and a projectable body fits the bound | UTF-8 text of the projected answer |
| `output_omitted` | `state == succeeded` and a projectable body existed but exceeded the bound, **or** serialization would exceed the tool budget after redaction | `true` means the run succeeded and an answer exists but is not in this view |

Rules:

1. Non-succeeded states never include `output` or `output_omitted`.
2. Existing fields keep their semantics and serialization (`failure_code`
   remains skip-if-none).
3. Older clients that ignore unknown JSON keys keep working; this is an additive
   wire change, not a tool rename.
4. Paths, prompts, variables, ownership, controller/lease material, target
   endpoint strings, and raw step `error` text never enter the projection.
5. Target profile names, run ids, journal paths, and step ids do not enter the
   MCP view either for this package (answer text only).

### Projection source and selection

Projection reads the **full durable journal** for the caller id (already loaded
by the daemon status path) and selects at most one answer string:

1. Require task `state == Succeeded` and journal status `Completed`.
2. Collect successful **single-target** steps that have a non-empty `output`.
3. Prefer the production case: exactly one such step → use that string.
4. If several succeed, use the lexicographically last step id among those with
   single-target `output` (journals store steps in a `BTreeMap`; this is
   deterministic without re-loading plan order). Fan-out-only steps
   (`outputs: Some(...)`) are ignored in this package so multi-target merges
   do not invent a synthesis rule.
5. If no projectable string remains, omit both fields (succeeded-but-empty is
   valid).

### Byte bound

Introduce one named constant shared by the projection helper and tests:

```text
WORKFLOW_VIEW_OUTPUT_MAX_BYTES = 64 KiB
```

- Count **UTF-8 bytes**. If the selected string exceeds the bound, set
  `output_omitted = true` and omit `output` (do not return a silent prefix).
- The daemon HTTP status envelope remains under the existing
  `API_RESPONSE_LIMIT` (256 KiB).
- MCP still serializes the whole `WorkflowView` through
  `serialize_json_bounded(..., MAX_TOOL_OUTPUT_BYTES)`. If the complete JSON
  cannot fit that outer budget after projection, return the lifecycle fields
  with `output` cleared and `output_omitted = true` rather than a hard tool
  error for an otherwise successful run.

### Ownership of logic

| Piece | Owner |
| --- | --- |
| Pure selection + bound | `vyane-workflow` helper (unit-tested, no daemon I/O) |
| Load journal on status / submit response assembly | `vyane-cli` daemon supervisor (`WorkflowTaskView` gains optional projected fields; summary stays body-free) |
| Public MCP types + redaction comments | `vyane-mcp` `WorkflowView` |
| Map daemon view → MCP view | `vyane-cli` `mcp_workflow` adapter |
| Fake control + real MCP duplex tests | `vyane-mcp` tests |
| Real MCP → daemon → synthetic target acceptance | existing CLI daemon workflow / MCP acceptance lane |

The MCP crate still owns no daemon discovery, token, path, or journal store.

## Delivery

1. Add `project_workflow_view_output` (name exact in implementation) and
   `WORKFLOW_VIEW_OUTPUT_MAX_BYTES` in `vyane-workflow`, with unit coverage for
   empty, single-step, multi-step last-id, fan-out ignored, oversize omit, and
   non-completed journals.
2. When building `WorkflowTaskView` for a succeeded task, project the fields
   from the full journal before discarding bodies into the summary.
3. Extend `WorkflowView` and the adapter mapping; keep cancel returning only
   lifecycle truth (no output requirement).
4. Extend `crates/vyane-mcp/tests/workflow_control.rs` fakes and assertions.
5. Extend the authenticated resident-daemon MCP acceptance path so
   submit → wait succeeded → status returns the synthetic provider answer and
   a privacy canary proves raw errors / paths stay out.
6. Document the additive fields in README MCP notes if the tool-result shape is
   listed there; update this package status to integrated after merge.

## Acceptance

1. A succeeded single-step durable workflow exposes `output` equal to the
   harness/provider answer through `vyane_workflow_status` over real MCP +
   resident daemon.
2. Non-succeeded status/cancel responses never include `output` or
   `output_omitted`.
3. An answer larger than `WORKFLOW_VIEW_OUTPUT_MAX_BYTES` yields
   `output_omitted = true` and no `output` body.
4. Projection never serializes ownership, controller, lease, paths, prompts,
   variables, or raw step errors on the MCP wire (unit + acceptance canaries).
5. Default six-tool library surface is unchanged; nine-tool CLI surface still
   exposes the same three workflow tool names with additive result fields only.
6. `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
   and `cargo test --workspace` pass on the exact implementation head.
7. Independent cross-model review of that head returns no open P0/P1 findings
   before merge.

## Non-goals

- A new MCP tool (`vyane_workflow_output`) or REST-only companion route as the
  product path (a future package may add a separate artifact endpoint if
  multi-megabyte answers are required).
- Streaming, partial progress, or output for failed / cancelled / timed-out /
  interrupted states.
- Fan-out multi-target synthesis, full per-step maps, or plan/prompt export.
- Changing request-bound dispatch/broadcast/failover tools.
- Putting answer bodies into the SQLite task store.
- Vyane Paw result-contract / evidence work (VP-15 phase two).
- Lock promotion inside this repository (consumer-side).
