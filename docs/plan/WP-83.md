# WP-83 · Native Harness trusted tools and Linux confinement

## Outcome

Turn the existing fresh, sessionless native AgentRun lane into the first usable
in-process coding harness slice. The public Rust implementation mirrors the
capability and safety boundary of Vyane's native harness without copying its
implementation or coupling the repository to private configuration.

In project terms, this is the self-built vyane-rs counterpart to Vyane's
**Canto**. It is not an adapter that invokes Vyane or Canto as an external
harness. WP-83A is only the first read/search slice of that counterpart, not a
claim that the full Canto-equivalent capability set already exists.

WP-83 is Linux-first and explicit opt-in. It keeps the existing provider /
protocol / harness / model axes separate: this package adds one native harness
implementation and does not change target resolution or replace the existing
Claude Code and Codex CLI harness adapters.

## Delivery stages

### WP-83A · Confined read and search

- Bind every tool operation to the admitted `PinnedWorkdir`.
- Add bounded `read_file` and deterministic workspace search tools.
- Reject absolute paths, parent traversal, NUL bytes, symlinks and mount
  crossings with Linux `openat2` beneath/no-mount/no-symlink resolution.
- Revalidate `NativeExecutionAuthority` at every filesystem-open boundary.
- Linux is the only supported enforcement platform; other platforms fail
  closed instead of degrading to path canonicalization.

### WP-83B · Confined edit and write

- Add `edit_file` by composing the existing pure `compute_edit` logic with
  guarded filesystem I/O.
- Add bounded new-file writes.
- Revalidate authority before opening the source and again immediately before
  atomic publication.
- Detect source replacement or modification between read and publish.
- Preserve fail-before-write behavior: ambiguity, drift, cancellation or
  authority failure produces no partial target update.

### Later required packages

Command execution and network access are required parts of the native harness,
but they are not silently bundled into the first filesystem package:

- a subsequent package adds bounded command execution, clean environment,
  process-group cancellation and Linux host confinement;
- a subsequent package adds explicit network policy and a web-search tool;
- both must use separate capabilities and approval rules, so granting file
  writes never implicitly grants shell or network access.

Session-aware resume, checkpoint/session commit and approval resume remain
separate work after the fresh/sessionless harness is complete.

## Permission model decision

WP-83 follows Canto's useful default: admitting a workspace grants native
read/search across that workspace, including dotfiles such as `.env`, `.npmrc`
and `.git`. A filename is not a reliable secret classification, so the trusted
tool does not carry a hard-coded, incomplete sensitive-name blacklist.

That broad default is adjustable. A native AgentRun submission may narrow it
with workspace-relative glob exclusions:

```json
{
  "native_permissions": {
    "filesystem_read": {
      "exclude": [".env*", ".git", "private/**", "**/*.pem"]
    }
  }
}
```

The exclusions are validated, frozen into the immutable native policy digest,
and enforced by both `read_file` and `search_files`. They can only narrow the
already admitted `PinnedWorkdir`; they cannot grant an absolute path, parent
traversal, symlink target or another filesystem. An excluded directory also
prevents recursive search from descending into it.

The complete native permission surface is deliberately split into independent
axes:

| Axis | Policy shape | WP-83A state |
|---|---|---|
| filesystem read | admitted roots plus path exclusions | implemented |
| filesystem write | writable roots, protected floors, allow/ask/deny rules | later |
| command execution | parsed command rules plus a host-enforced sandbox | later |
| command network | destination policy enforced below the shell | later |
| web search/fetch | separate tool and domain/source policy | later |

Future user, project and managed configuration layers will resolve these axes
into one frozen per-run policy. A managed deny/floor cannot be weakened by a
project or request override. Tool-level `allow`/`ask`/`deny` remains distinct
from OS enforcement: approval changes whether an operation may be attempted,
while the sandbox/capability boundary limits what the operation can actually
reach.

## Safety contract

- Path strings are input, not authority. Filesystem effects derive from the
  opened pinned workdir and descriptor-relative operations.
- Permission matching is only a policy decision. The trusted tool must enforce
  the actual arguments and capability boundary itself.
- Every open, publish and later spawn/network linearization point independently
  revalidates live native authority.
- Read-only mode exposes only read/search. Write mode may additionally expose
  edit/write. Full mode does not acquire shell or network capability until the
  later packages explicitly assemble them.
- Tool results are bounded and never expose content reached through a path
  outside the admitted workspace, a configured exclusion or raw host errors.
  Ordinary workspace files remain inside the default read capability; the tool
  does not claim to recognize every possible embedded credential.

## WP-83A verification gate

- Acceptance tests prove ordinary read/search behavior through the real
  authorized `NativeTurnDriver` and resident HTTP AgentRun lane.
- Adversarial tests cover absolute paths, `..`, symlink escape, configured path
  exclusions, path replacement, special files, oversized input/output,
  cancellation and authority revocation.
- Mutation-sensitive tests prove the exact count and ordering of
  registry/component/read-open authority checks; removing one changes the
  expected result or permits the revocation fixture to disclose content.
- Unsupported platforms fail before a model or tool side effect.
- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
- The exact PR head receives independent cross-model approval and all required
  GitHub checks before merge.

WP-83B will add its own gate for edit/write success, source drift, atomic
publication and fail-before-write behavior. WP-83A does not claim those tests
or capabilities.

## Current implementation status

WP-83A is implemented on its isolated branch and has local read/search,
configurable exclusion, adversarial, real HTTP-to-tool-to-completion, workspace
test and lint evidence. It is not complete until the exact committed head
passes independent review and the required GitHub checks. WP-83B and the
command/network packages remain future work.

## Explicit exclusions

- no claim of whole-system parity;
- no default switch away from existing CLI harnesses;
- no native session resume, checkpoint publication or approval replay;
- no unrestricted shell or implicit network access;
- no private path, provider, credential or deployment material in this public
  repository.
