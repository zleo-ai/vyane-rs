# WP-101 — bound ambiguous AgentRun submission retries

## Outcome

Keep daemon AgentRun acceptance submissions reliable under suite load without
turning an ambiguous HTTP timeout into either an unbounded wait or a second
logical run.

Production daemon behavior and endpoint semantics do not change.

## Failure evidence

After terminal status polling was bounded in WP-100, the full Linux CLI suite
exposed the same transport symptom earlier in the lifecycle: a
`POST /v1/agent-runs` response timed out after 15 seconds while the daemon was
under test load.

Every accepted submission already carries a caller-supplied UUIDv7 `run_id`,
and the daemon treats an exact replay of the same frozen request as idempotent.
The acceptance fixture can therefore retry only timeout/connect failures with
the same body and identity. Other transport errors and all HTTP responses
remain final for the attempt.

Repeated suite validation also exposed that the process-restart fixture allowed
only 15 seconds for a production recovery pass whose configured hard bound is
20 seconds plus a 5-second settlement margin. Its polling budget now covers
that existing bound; no recovery timeout or production behavior changes.

## Acceptance

1. Submission attempts reuse one HTTP client and the exact same request body.
2. Each attempt has a short timeout and all retries share one strict total
   budget.
3. Only timeout/connect failures retry; HTTP responses and other client errors
   are returned immediately.
4. A delayed-first-response regression test proves an ambiguous timeout retries
   the same request and returns within the total budget.
5. The process-restart fixture allows the full configured recovery observation
   and settlement window.
6. The full daemon acceptance suite, workspace gates, parity, independent
   review, and cloud CI pass on the exact committed head.
