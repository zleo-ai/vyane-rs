# WP-467 — rmcp 3.3 and MCP 2026 dual-era handshake

## Outcome

Refresh the locked MCP SDK from `rmcp` 3.0.1 to 3.3.0 and pin Vyane's stdio
server to the dual-era MCP 2026 negotiation rule:

- `initialize` stays on the 2025-11-25 legacy lifecycle, even when a client
  offers `2026-07-28`.
- `server/discover` advertises every SDK-known revision through
  `2026-07-28` and can negotiate that revision for modern clients.

The six-tool library and nine-tool CLI surfaces, stdio transport, and
owner/credential/authority boundary do not change. Streamable HTTP, OAuth,
Tasks, and other 2026 optional capabilities stay unused.

## Why 3.3

`rmcp` 3.0 already models the 2026-07-28 wire types, but `LATEST` is still
`2025-11-25`. Later 3.x releases tighten initialize so it cannot settle on
`2026-07-28` (that revision uses discover / per-request metadata instead)
and add `ServerHandler::negotiate_initialize`. 3.3.0 is the current stable
crate on that line and keeps the Rust 1.88 MSRV.

Vyane previously named `ProtocolVersion::LATEST` in `get_info`. That alias
is the correct *legacy* default today, but it is not a 2026 pin. This
package names `V_2025_11_25` for initialize and
`ProtocolVersion::known_up_to(&ProtocolVersion::V_2026_07_28)` for the
advertised set.

## Compatibility

This repository is still an explicitly unstable pre-release. The workspace
dependency becomes `version = "3.3"` so a lock refresh cannot silently
fall back to 3.0.1. The 3.3 crate remains API-compatible with the existing
`#[tool]` / `ServerHandler` / stdio client test surface; the compile delta
is the lock plus the explicit version methods.

Auth features (`auth`, Streamable HTTP) are not enabled. Existing MCP
clients that only speak `initialize` keep working on 2025-11-25.
